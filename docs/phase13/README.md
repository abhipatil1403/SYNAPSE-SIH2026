# Public landing page and interaction finishing pass

This release updates the existing application in its original neutral/forest-green theme. It does not activate complaint reads, expose source tables, change Auth identities/roles or enable hosted business writes.

## Changes

- `/` is a public landing page instead of an authenticated dashboard redirect. It includes an original animated workflow illustration, process narrative, all existing workspace destinations, account links, FAQs and a responsive menu. The illustration is explicitly identified as an illustration and contains no invented dashboard statistics or live records. Public visits do not mount the operational data provider.
- Lucide is removed from source, dependencies and the lockfile. Authentication pages and sidebar labels no longer use decorative library icons. Necessary controls use small local typographic/CSS marks with their existing accessible button labels. Dashboard geometry, chart calculations and original color tokens are preserved.
- Profile and notification panels dismiss on pointer interaction outside, focus leaving the panel, Escape and route changes. Escape returns focus to the trigger. Native dialogs use unique heading IDs, return focus to connected triggers and distinguish actual backdrop clicks from dialog padding. Mobile landing navigation also dismisses outside/on Escape.
- One root toast system serves Auth, profile, operational panels and Demo Mode. Up to six messages stack at the existing bottom-center location. Messages can be dismissed, announce status/errors, pause expiry on hover/focus and remain visible above native dialogs using the browser top layer. Persistent data availability and loading states remain in context; transient save/error messages move out of page headers.
- Shared action forms await asynchronous submit handlers, lock against duplicate submissions, disable fields while pending and display a spinner. Auth, profile, logout, refresh, administrative loading and processing checks have explicit pending states. The operational command provider also guards concurrent submission synchronously. Existing idempotency keys and permission checks are retained.
- Sidebar transitions show a real pending indicator and a short page entrance. Landing path/card/section motion, popover motion and toast entrances respect reduced-motion preferences. Automatic prefetch remains off for protected sidebar/account links and the landing workspace directory.
- Auth forms have a text-led layout, password visibility control, matching-password validation, native field constraints, bottom error feedback and busy states that continue through successful navigation. `/signup` reads the actual runtime registration switch; a closed registration policy is explained before asking for a password.
- Hosted pages no longer repeat the generic approved-account paragraph. Working pages render their actual content. Unavailable pages distinguish complaint-preview approval from an unimplemented hosted workflow and link to `/help#workspace-access`. The membership page shows only actual authorized self-directory data. Notification/search empty states do not imply that unavailable case data was successfully queried.

## Why complaint pages may still be unavailable

**Officer approval is not complaint-preview activation.** Signing in again, deleting/recreating users, changing the Site URL or elevating an officer cannot complete a backend integration. A System Administrator can review officer membership/role windows through `/admin`, but has no automatic right to read all cases.

The deployed read preview remains gated by `SYNAPSE_PHASE1_READ_ENABLED`, the exact verified Auth subject allowlist `SYNAPSE_PREVIEW_AUTH_IDS`, and an independently approved expiring SQL lease. Do not change these solely to remove a message. The positive hosted case authorization/acceptance, natural expiry soak, independent review and previously documented Phase 11 blockers must be resolved first. The private gateway still uses the restricted Supabase login and verified transaction pooler; the public URL and publishable key alone do not replace that architecture.

Intake, tasks, documents, AI operations, coordination and complaint mutations also require their remaining hosted workflow implementations and release tests. Enabling the case read preview does not implement or authorize those operations. Global Live Mode and hosted business writes remain disabled. The existing isolated local workflows and Demo Mode have not been migrated or silently copied into Supabase.

Public registration is a separate policy: `SYNAPSE_SIGNUP_ENABLED=false` intentionally displays invitation-only information. If the owner approves public development registration, configure that server-only variable to `true` for the target environment, confirm the existing provider signup/email policy and redeploy. New registrants still receive no privileged membership during signup. Do not add operator/service-role credentials to the web service.

## Manual acceptance — owner to execute

Browser, mailbox, real-account HTTP and hosted authorization interactions were **not executed for this release**, at the owner's request. Updated browser source expectations are retained for future use; their presence is not an executed pass. Historical Phase 12 acceptance is not evidence for the new UI.

1. After Vercel deploys the feature branch, open `https://synapse-sih-2026.vercel.app/` and hard refresh. Confirm it stays on the public landing page while signed out. Test each header anchor, workflow animation, footer/account link and mobile menu. Test at 1536, 768 and 390 pixels. Enable reduced motion and confirm content remains readable with animations stopped.
2. Open `/login`, `/signup`, `/forgot-password` and `/reset-password`. Confirm no ornamental icons, usable labels, password show/hide, keyboard focus and clear signup-policy information. Submit invalid credentials and mismatched reset passwords; feedback should appear at the bottom. Do not share passwords or recovery links. Test email recovery in the same browser that requested the actual link.
3. Sign in with an existing approved officer. Switch sidebar pages; expect the pending bar and short entrance, then the correct active item. Clicking repeatedly must not create duplicate submissions. On a slow connection, form/refresh controls must show pending state.
4. Open the profile menu and Notifications. Click outside, tab out and press Escape in separate attempts. Each should close; Escape should return focus. Navigate through a menu link and confirm the panel closes. Notification data must be labeled unavailable on the account-only deployment.
5. In `/settings`, save a permitted display-name change. Expect a spinner/disabled save control, then a bottom success toast and updated profile. Trigger another message before dismissing the first and confirm the messages stack. Hover/focus a toast to pause expiry; use its close button. Confirm a modal error toast appears above the dialog.
6. Use Calendar month navigation/Today and date selection. In account-only mode, dates work but events must be identified as unavailable. Dashboard values remain **—** until the separately authorized case preview is enabled.
7. As the existing Development System Administrator, open `/admin`. Confirm loading/failure/empty states are distinct. If making a separately authorized test-account decision, choose a real Bureau, role, future expiry and meaningful reason; expect pending state and bottom feedback. Ordinary officers must still be denied administrator operations. Do not elevate the two Case Officers or approve a new identity as part of this visual check.
8. Open `/help#workspace-access`. Verify the distinction between account approval, complaint preview and missing hosted workflows. No button should claim to activate those permissions. Preserve disabled hosted business writes and all Phase 11 restrictions.
9. If checking local business workflows, use only the existing isolated development environment. Regression-check a permitted intake/task/profile/calendar operation, duplicate-click prevention and form error feedback. This is separate from hosted write authorization.

The release report records executed unit/static/build checks and the exact GitHub head separately from these pending human checks. No claim of complete hosted complaint-management readiness is made.

# Canonical Supabase workflow adapter

The existing original-dashboard `PlatformEngine` now has a canonical PostgreSQL adapter (`lib/hosted`), rather than copying the isolated workbench JSON store into hosted Supabase. It uses the existing verified Supabase Auth session and trusted internal profile. The Demo actor selector is not used. No service-role web credential is used.

`20261027171357_phase14_canonical_operations.sql` is additive and starts closed: `operations_control.enabled=false`, `writes_enabled=false`. `SYNAPSE_HOSTED_OPERATIONS_ENABLED` must also remain false until the independent hosted release review passes. Existing protected public read RPCs remain closed; their old preview switches are not used to unlock this adapter.

The dedicated NOLOGIN/NOINHERIT/NOBYPASSRLS runtime owns no tables. Source schema is not exposed through PostgREST. The exact column grants are in SOURCE_ACCESS_MANIFEST.json; UPDATE/INSERT grants match the static persistence operations, and authorization-critical source directory rows are immutable to this role. Existing PUBLIC policies on those source tables are restricted to their original application/ingest principals so a new runtime cannot inherit the legacy global-admin case bypass. Existing function definitions remain unchanged. Source legacy privileged mutator EXECUTE grants are narrowed from PUBLIC to the original application/ingest roles.

The adapter disables JIT within its scoped transaction to avoid LLVM compilation overhead for nested RLS plans, and projects each static collection separately rather than constructing one enormous authorization plan. It reads authorized source rows under RLS, runs the existing command engine, and atomically writes canonical records, source history, notifications, audit, version checks and idempotency receipts. Actual case numbers come from the existing sequence; bigint values remain strings. Global System Administrator remains configuration-only. Intake review ownership is distinct from the service that fetched an email; no service impersonates an officer.

The new private tables hold release control, idempotency receipts, scheduled calendar activities, evaluation fingerprints, bounded protected file bytes and provider-processing job records. They do not replace the canonical complaint tables. Hosted files are limited to 2 MB; binary files remain quarantined without an actual scanner verdict. Unsupported Gmail attachments remain in the original submission quarantine instead of being falsely marked safe or inserted as supported evidence.

## Verification and limits

Run `npm run test:database:operations` against the dedicated loopback test cluster. It reconstructs the deployed baseline in a fresh UUID database, runs the earlier Auth/approval/readonly security suites and the canonical/OAuth migrations and the separate active-Bureau correction, then exercises canonical intake, registration, tasks, calendar, SLA, disposal, version concurrency, receipts, Gmail draft persistence, attachment linking, two-Bureau direct SQL isolation, independent transfer approvals, post-transfer source/attachment denial, suspension and session revocation. Managed Auth and claims are explicitly synthetic in this suite; it does not prove real issued-JWT browser acceptance.

`local-database-results.json` binds the actual tested SQL hashes. `scripts/phase14/apply-reviewed.mjs` requires fresh matching evidence, captures a private pre-migration schema/count/function baseline, checks all existing source table counts and original function definitions remain unchanged, and tests private ownership/grants/release defaults. Without `--apply-reviewed` it rolls the complete hosted transaction back. The applied/dry-run result is recorded in ../phase15/MIGRATION_REVIEW.json.

The hosted adapter is a gated implementation, not a claim that every operational workflow has production acceptance. Remaining activation work includes current issued-JWT positive workflow verification, independent transactional/RLS review, attachment scanner provisioning for binary verification, provider-job execution/retry/review acceptance on hosted data, metadata-only cross-Bureau discovery and scale/paging review. The existing workbench provider worker remains loopback-only; no serverless process silently starts that worker. Do not enable Live Mode or complaint writes while these checks are unresolved. Gmail OAuth consent itself is separately available to a current configuration administrator.

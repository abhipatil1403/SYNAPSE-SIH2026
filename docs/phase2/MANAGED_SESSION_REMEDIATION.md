# External session invalidation — operator procedure

**Design proposal only; no corrective migration has been created or applied.** The sign-off test proved that provider-only logout removes the provider session but leaves an otherwise unexpired JWT able to call `public.synapse_phase1_cases`. Application logout is protected by SYNAPSE tombstones. Keep both read gates and all business writes disabled until this lifecycle boundary is resolved and retested.

The deployed `auth.sessions` table is owned by `supabase_auth_admin`, has RLS enabled and currently has no policies. The authorized operator can read it, but cannot assume its owner role. Granting unrestricted access to the registry role, introducing a BYPASSRLS role, or placing the operator secret in the web process would violate the current security design. None was done.

## Required correction

1. Obtain an authorized managed-schema owner route or Supabase-supported session-validation mechanism. Restore connector access for managed advisor output if available; a catalog equivalent does not establish managed-schema ownership rights.
2. Have that authorized owner review a narrowly scoped session-liveness boundary. A suitable database design uses a dedicated NOLOGIN/NOINHERIT/NOBYPASSRLS role, owning no tables, with USAGE only on required private schemas and SELECT only on the verified session ID/user ID columns of `auth.sessions`. Its role-specific SELECT policy must match **both** the verified gateway subject and session ID. Existing RLS must remain enabled. The registry and browser roles receive no managed-session table access.
3. Expose only a parameterless **private** boolean helper owned by that restricted role, with empty `search_path` and `row_security=on`. It must resolve identity through the existing gateway-verified helpers, not client parameters, user metadata, email or `synapse.user_id`. Only the registry role may execute it. The helper checks the current session's existence and applicable current provider expiry conditions; it returns no session rows, refresh tokens or other users' metadata.
4. Require this liveness check in `synapse.phase1_auth_subject()` so both existing read RPCs reject provider-revoked sessions. Keep the logout RPC narrowly scoped and idempotent. Do not expose the private helper through PostgREST or GraphQL.
5. Generate a new versioned migration using the CLI, review its exact hash, test it on a disposable baseline and the authorized hosted test environment, and preserve all existing migrations/history. Document a forward corrective rollback; never delete or rewrite applied history. If Supabase does not support the proposed managed-schema policy, stop and select a supported architecture rather than disable RLS.
6. Update the SQL authorization fixture to explicitly model provider-session liveness **inside its rolled-back transaction**. Keep that evidence separate from the actual issued-JWT runner. Do not call simulated liveness an actual Auth pass.
7. Rerun `signoff-negative.mjs --controlled-read`. The `external_logout_session_invalidation` check must pass: after provider-only logout, the exact previous JWT must receive authentication rejection, while the second Bureau retains only its own authorized case. Also rerun refresh rotation, application logout replay, suspension, role and identity revocation, membership expiry, SQL grants/RLS and the original-token expiry check.

This proposal requires security/managed-schema-owner review; it is not executable approval or a request to bypass the current permission boundary. Session time-box/inactivity policy and externally cached already-delivered data need their own documented operational semantics.

Supabase documents the session-ID/`auth.sessions` relationship and the need for a live-session check for immediate sign-out guarantees in [User sessions](https://supabase.com/docs/guides/auth/sessions#how-to-ensure-an-access-token-jwt-cannot-be-used-after-a-user-signs-out).

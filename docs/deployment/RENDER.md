# Render free web service + existing Supabase

There is no additional PostgreSQL service to buy. Supabase already hosts PostgreSQL and Auth. This repository's `render.yaml` creates only one **Free Node web service**, with no Render database, persistent disk, paid worker or translation service. No resources are created by committing this file.

## Current implementation boundary

The current hosted account gateway connects to the **same Supabase database** with the restricted `synapse_web_login` role. That URL is not a second database or an operator/service-role bypass. It supplies the existing audited identity, session revocation, approval and role-management functions.

The URL and public publishable key configure the Supabase client. After sign-in, the actual user's issued JWT authorizes protected Data API requests through RLS or reviewed RPCs. An unauthenticated key alone must not grant complaint access. The current application specifically expects an `sb_publishable_...` key in `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`; do not substitute a legacy JWT anon key without adapting and testing that validation.

Hosted workflow support is **not complete**: the generic platform read/write gates remain closed and generic business RPCs remain unimplemented. [Phase 11](../phase11/README.md) adds a private authorized read-only path: approved accounts can load the original shell, Settings/profile and authorized User Approvals. Case/SLA data requires an explicit server allowlist and approved expiring SQL lease; full hosted business workflows remain disabled. The working local Workbench is preserved separately. Deployment is not a claim that every feature is hosted.

## Exact deployment steps

1. In [Render](https://dashboard.render.com/), choose **New → Blueprint** and connect `abhipatil1403/SYNAPSE-SIH2026`.
2. Select branch `feature/synapse-phase3-5-platform`, with Blueprint path `render.yaml`.
3. Review the preview: it must contain **one Free web service and zero databases/workers/disks**. Stop if different resources or charges are shown.
4. Supply the prompted values below. `SYNAPSE_AUTH_RATE_SECRET` is generated by Render; do not paste or commit it.
5. Confirm the actual assigned `https://...onrender.com` service URL. Set `SYNAPSE_APP_ORIGIN` to that exact origin, without a path or trailing slash, then redeploy.
6. In Supabase **Authentication → URL Configuration**, set Site URL to the same HTTPS origin and allow `https://YOUR_SERVICE.onrender.com/auth/callback?flow=recovery`. Preserve the localhost recovery callback. Do not change Confirm Email, grants, assignments or RLS as part of deployment.
7. Visit `/login`. Verify real login/logout, refresh, HTTPS cookie properties and recovery in the requesting browser. `/api/health` is liveness only. A 200 health response does not prove database/workflow availability.

If creating a Web Service manually instead: choose **Node**, **Free**, the same repository/branch, repository-root working directory, build command `npm ci --include=dev && npm run build`, start command `npm run start`, and health check `/api/health`. Render sets `NODE_ENV=production`; explicitly including development dependencies preserves the TypeScript and Tailwind build tools. Set `NODE_VERSION=22`. Next.js already binds `0.0.0.0` and accepts Render's `PORT`; do not run `workbench:start` or a local database setup script on Render.

## Environment values

| Variable | Value/source |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Already set to the existing SYNAPSE project by the Blueprint |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | Existing `sb_publishable_...` value in ignored `.env.local` |
| `SYNAPSE_APP_ORIGIN` | Actual assigned `https://YOUR_SERVICE.onrender.com` origin |
| `SYNAPSE_GATEWAY_DATABASE_URL` | Existing restricted **Supabase** URL in ignored `.env.gateway.local`; keep its URL-encoded password and pooler host/port. Do not replace it with a Render database or the `postgres` operator URL. |
| `SYNAPSE_GATEWAY_CA_PEM` | Entire public certificate in `.local/phase2/supabase-db-root.crt`, including BEGIN/END lines; leave the local CA file-path variable unset |
| `SYNAPSE_AUTH_RATE_SECRET` | Generated automatically by Blueprint; manual deployment requires a random secret of at least 32 characters |

Keep `SYNAPSE_TRUST_PROXY=false` until the actual Render ingress/client-IP overwrite behavior is verified for this service; shared-ingress rate limiting remains active. Keep `SYNAPSE_SIGNUP_ENABLED=false`, `SYNAPSE_PHASE1_READ_ENABLED=false`, `SYNAPSE_WORKBENCH_ENABLED=false`. Do not import entire local env files or add operator, service-role, worker, Gmail, model-provider or HF credentials to the web service. A public publishable key is intended for the client; private database credentials remain server-only.

## Supabase-only implementation still required

- Implement reviewed transactional snapshot/command contracts against the existing schema, with precise authenticated grants, fixed search paths and Bureau/document scope. Do not expose all 69 tables or install the local Workbench SQL into Supabase.
- Preserve server-verified Supabase identity, active officer approval, session revocation and independent role decisions. Never authorize using browser role selection or a service-role client.
- Reuse the existing frontend contracts/selectors and preserve exact record/lifecycle shapes. Move operations away from the local-only data adapter through tested migrations, not by relaxing its loopback restrictions.
- Run actual issued-JWT, post-logout replay, suspension, revocation, two-account and transactional workflow tests before opening any hosted gates.
- Schedule provider jobs separately using an explicitly reviewed Supabase-compatible execution model. Free Render web instances sleep and do not establish a reliable durable-worker runtime; local IndicTrans2 models do not move into the web process. Gmail remains off pending mailbox approval.

No separate paid database is required for this architecture. Capacity and free-tier limits still apply. No hosted workflow activation or provider deployment is claimed by this Blueprint.

Local deployment checks: the YAML parsed as one Free service and zero databases. The existing production build started with `PORT` supplied through the environment and bound `0.0.0.0`; `/login` and liveness returned 200 while `/api/workspace/snapshot` returned the expected locked 503 with hosted Live Mode false. The source/build/staged credential scan passed. This is not an executed Render deployment or proof that hosted complaint workflows work.

# Application-owned officer authentication boundary

The Phase 2 defect is real: provider-only logout does not write SYNAPSE's session tombstone. The earlier `auth.sessions` candidate is still unapplied and the current operator still cannot manage that protected table. This alternative changes only application-owned schemas/functions/roles.

## Reviewed boundary

The correction **revokes `authenticated` execution of both protected public read RPCs**. Existing anon/service/PUBLIC restrictions remain. A browser JWT, valid or revoked, cannot enter either read RPC. No managed-session ACL, policy, trigger or object is modified.

The server first performs online Supabase `getUser()`, verifies confirmed email, binds token subject/issuer/audience/expiry/session ID to the returned user, then calls a private SQL gateway through a separate restricted database login. The gateway receives claims only from this trusted server, never from a request body. It executes reads as the existing NOLOGIN/NOBYPASSRLS reader, which owns no source tables, has narrow columns, uses empty `search_path` and retains all RLS and expiring read-lease checks. Current membership/roles/mapping/status and application tombstones are rechecked in SQL. No browser-selected Demo identity participates.

The login may assume only `synapse_web_gateway`; it has no source-schema USAGE, no direct table grants and cannot assume the reader or account manager. It can invoke four private gateway entry points: read, account, rate limit and membership review. The internal account implementation remains separately uncallable. The credential is a privileged **server trust boundary**: compromise would allow forged identity assertions, so it requires verified TLS, restricted secret storage, rotation, no browser/public environment prefix and access-controlled deployment. It is not an operator/service-role key and cannot bypass RLS or call arbitrary legacy operations.

Onboarding uses a distinct NOLOGIN/NOBYPASSRLS account-manager owner with selected identity/configuration columns and four RLS-protected application tables. Only independent, current GLOBAL `SYSTEM_ADMIN` authority can approve/deny/revoke. It cannot read complaint bodies/documents. Requests never create memberships automatically; approval atomically records exact Auth UUID, internal user, Bureau membership, bounded role and append-only decision audit. Existing emails/mappings fail closed for explicit reconciliation. No production administrator is invented or bootstrapped by the migration. The follow-up `20261026161408_phase6_approval_authority_lock.sql` holds shared locks on the approving user's active account/link and GLOBAL assignment until the decision transaction ends; competing suspension/revocation waits or aborts. A separate-connection lock-timeout test executed locally. The internal implementation has no gateway/API EXECUTE grant.

Password recovery requires a successfully exchanged PKCE recovery flow (provider-reported redirect type) or verified one-use recovery OTP. It creates a 15-minute session-bound application grant, consumed before the password update; replay is rejected. A provider failure after consumption requires a fresh recovery link. Password updates are followed by global provider logout. Public registration is operator opt-in. Login, signup and reset have database-backed limits plus Supabase's own limits; proxy headers are trusted only behind an explicitly configured ingress. Deployment CAPTCHA/MFA/SMTP policies still require operator validation.

The installed SDK's multi-flow recovery option is explicitly enabled (`appendPkceFlowIdToRedirects`); callbacks validate its `sb_flow_id` rather than accepting a browser-supplied identity. An installed-SDK contract simulation covers competing verifier slots. Legacy single-flow callbacks remain supported. Callback failures do not silently invalidate an unrelated existing session.

The user explicitly authorized a third development administrator. Real signup, human mailbox verification, provider confirmation checks and a privilege-free Pending Approval login preceded operator bootstrap. The bootstrap validates the private approval plan and exact Auth UUID, refuses an unexpected existing administrator, audits the bounded GLOBAL configuration assignment and preserves both original CASE_OFFICER accounts. The administrator has no Bureau membership and reads zero cases in real hosted tests. Membership management uses independent current authority, optimistic expiry checks, idempotency and an immutable review record; it never changes role codes. A hosted unchanged-expiry review, matching retry and conflicting retry passed.

## Review and test limits

An additional restored-database negative test reproduced a separate scope defect: an officer's assignment could pass `phase1_can_read_case` with only a different Bureau's current role. `20261026165409_phase6_officer_bureau_scope.sql` corrects that Phase 1 helper, requiring current target-Bureau membership and role for ordinary officer assignment reads. Explicit DETAILS/COORDINATE grants retain their separate semantics. The predicate test failed before the correction and passed afterward; no hosted case was reassigned to manufacture that scenario. Existing two-account hosted positive/negative checks are rerun after application. All 30 original legacy function definitions remain unchanged.

`npm run test:database:auth` replays the baseline and all prior migrations, runs the original 69 assertions, then applies the correction in a fresh loopback database and verifies direct-RPC denial, private gateway isolation, no automatic mapping, administrator checks, approval/revocation persistence, conflict detection, audit, one-use recovery and throttling. These synthetic claims are **not real hosted JWT evidence**. Hosted login, provider-only logout, replay, refresh and two-account tests must separately pass before any read-preview activation decision. New business writes and the global Live Mode flag stay off regardless.

To apply the exact reviewed hash: run `node --env-file=.env.local --env-file=.env.operator.local scripts/phase6-7/apply-gateway.mjs --apply-reviewed`. This uses the already authorized operator only for application migration/role provisioning. It verifies closed gates and current grants, records exact migration history, provisions a random restricted login, and writes ignored `.env.gateway.local` plus a DPAPI recovery vault. Run the web server with `node --env-file=.env.gateway.local node_modules/next/dist/bin/next start --hostname 127.0.0.1 --port 3000`; never load `.env.operator.local` into a web process.

Rollback: first keep both read gates off, revoke the restricted login's gateway membership (or NOLOGIN it), and stop the runtime. Do not regrant browser RPC execution: that reopens the known defect. Preserve account/decision/recovery records. Prefer a forward corrective migration, and do not rewrite applied history or reset the database. The original managed-table candidate remains historical/unapplied and must not be run alongside this alternative without a new review.

# Hosted account workspace and reviewed read-only projection

**Hosted complaint writes: OFF. Global Live Mode: OFF. Complaint preview allowlist and database read lease: not activated. Manual acceptance: AWAITING USER MANUAL TESTING.**

## Fix for the deployed 503

The old `/api/workspace/snapshot` path required the globally locked generic platform RPCs, while the working original UI used a loopback-only database. The hosted database had neither generic platform RPC implementation. A successful deployment therefore still returned the intentional `platform_locked` 503.

`lib/platform/hosted-readonly.ts` now handles the hosted path through the existing approved Supabase account gateway. It first performs online `getUser` verification, trusted JWT/subject mapping and current approved-role/profile resolution. Accounts not explicitly included in server-only `SYNAPSE_PREVIEW_AUTH_IDS` receive a projection of their actual self profile with `workspace.mode=ACCOUNT_ONLY`; no case query is performed. An empty preview allowlist never becomes global access.

This projection is deliberately distinct from an authorized empty complaint repository. The original shell renders, Settings/profile and authorized User Approvals work, while Overview explains that complaint access awaits review. KPI zeros, AI totals or empty task/activity records are not presented as if those hosted features had been queried. Unsupported routes display an integration notice. Local operational behavior remains unchanged.

Only when the existing server switch `SYNAPSE_PHASE1_READ_ENABLED=true` **and** the verified subject is explicitly allowlisted may the server call the new private `synapse_gateway.workspace(jsonb)` function. It returns account-only metadata while the existing SQL `read_enabled` gate is false or `read_until` has expired. All three controls are required for `READ_ONLY` case data. No browser actor/role, public client setting or request body can set those server controls. They remain inactive.

## Migration review

`20261027124140_phase11_readonly_workspace.sql` was generated by the Supabase CLI, tested against a disposable reconstruction and applied as an additive reviewed migration. Candidate and migration bytes are identical. `MIGRATION_REVIEW.json` records the exact hash, applied ownership/grants, unchanged original function definitions/business row counts and closed activation settings.

- One function in the **unexposed** `synapse_gateway` schema; no public RPC or schema exposure.
- Owner: existing `synapse_case_reader`, NOLOGIN, NOINHERIT, NOBYPASSRLS, no source-table ownership; fixed empty search path and `row_security=on`.
- Execute: existing private web gateway only. PUBLIC/anon/authenticated/service-role execution is revoked. Temporary installation authority is removed.
- Column-only additional reads: case summary/disposal timestamp, institution state, and SLA identifier/policy/original due timestamp. Existing case/Bureau/institution/category/SLA RLS policies remain intact. No document, evidence, work-item, Auth-managed or business-write privilege is added.
- SQL serializes explicit fields under the existing active identity, role, Bureau membership, assignment/grant and session-revocation rules. SYSTEM_ADMIN has no automatic case privilege.
- Case numbers and versions remain decimal strings. Original summary and disposal/SLA dates are preserved. Deployed SLA `MET` and `CANCELLED` codes are retained exactly; neither produces an active calendar deadline.
- Projection supports cases, their RLS-visible institution/Bureau/category references, and case-level SLA only. Other arrays are labelled unavailable by capabilities and are not claimed as connected sources.
- More than 5,000 authorized cases or 4 MiB of case source text rejects the projection instead of silently truncating metrics. This is a bounded prototype projection, not a production-scale reporting/transport guarantee; final response size, paging and load acceptance remain open.

Existing generic `activation.reads` and `activation.businessWrites` stay false. The new read-only repository unconditionally rejects complaint commands. The existing hosted command endpoint and local-only attachment/job/config endpoints remain locked. The browser also prevents complaint commands in the labelled hosted workspace; this complements, rather than replaces, server enforcement. Account self-name and independently authorized officer decisions retain their existing private endpoints.

## Deploy this fix

Deploy the new feature-branch head after CI passes, using the existing Supabase URL/publishable key and restricted gateway URL/CA/rate-secret settings. No additional database, paid service or new required environment variable is needed. Set `SYNAPSE_APP_ORIGIN` to the exact HTTPS origin of the deployment being used. Preserve the server preview allowlist as empty until its owner review; do not switch on the database read lease or complaint write gate to make the notice disappear.

After deployment, an approved account should receive HTTP 200 with `workspace.mode=ACCOUNT_ONLY` from `/api/workspace/snapshot`, see the original shell and be able to open Settings. The approved administrator can open `/admin`. Unauthenticated sessions remain 401, current-approval failures 403, and hosted complaint commands remain 503. Configuration/provider failures may still return a genuine 503; those require their own deployment evidence.

Full hosted intake, tasks, evidence, scheduled activities, AI, coordination, disposal and exports still need transactional integration and hosted acceptance. Existing local PostgreSQL records are preserved and are not silently copied into Supabase. Gemini/IndicTrans2 development tests from Phase 10 are not proof of hosted provider deployment.

# Phase 16 — connected workflow completion and private scanning

The existing dashboard, routes, Demo environment and canonical Supabase adapter are retained. This release adds authenticated server processing, limited metadata discovery, private scanner provenance and actual-deadline reminders. It does not substitute mock production data or remove authorization gates.

## Implemented behavior

- Protected server requests require provider-current refresh authority followed by online user verification and validated issuer/subject/session/expiry. A signed logged-out JWT alone cannot establish application access. Supported Supabase SSR cookies carry rotated tokens; managed Auth tables and their ownership are unchanged.
- Draft creation and source changes queue durable translation/matching jobs. Actual Google Cloud Translation output and Gemini embedding similarities are stored with source version, provider provenance and mandatory human review. Candidate selection uses institution, recency and indexed lexical matching under current RLS. There is no automatic merge. Provider calls run outside SQL transactions; identity, lease, source version and authority are checked again before commit. Processing status, retries and errors appear in original Intake.
- Limited cross-Bureau discovery returns only explicitly discoverable case IDs/numbers, institution/category/Bureau IDs. It cannot return complaint descriptions, evidence or personal details. Independent Bureau-head approval grants only the requested expiring scope; revocation removes it. System Administrator remains configuration authority, not a complaint-access bypass.
- Actual uploaded and ingested attachment bytes remain PENDING until a private scanner returns a schema-valid CLEAN receipt matching their hash and size. Text is also scanned in hosted mode. Evidence verification and protected downloads enforce clearance. Registration copies a scan receipt only for identical Gmail attachment bytes. Missing service, infection, timeout, malformed or indeterminate results never clear quarantine.
- Reviewed reminder rules use actual authorized SLA dates and active mapped officers/Bureau heads. Database receipts prevent duplicate reminders. No inferred policy durations, fabricated events or automatic closure are introduced. The existing Vercel daily cron and an additional daily reminder cron require CRON_SECRET; no paid scheduler was created.
- The account service checklist reads current catalog/ACL/control/mailbox observations and dated executed session evidence. A configured key is distinguished from a completed provider job. The experimental document view-transition opt-in was removed; existing route entrance/hover motion and reduced-motion support remain. The reported browser exception was not reproduced through browser automation.

## Reviewed database changes

Three additive migrations were generated with the Supabase CLI, replayed against the original baseline, exercised in disposable PostgreSQL and applied through `scripts/phase16/apply-reviewed.mjs`. The script first writes a private metadata/count/function baseline, checks exact tested candidate/migration hashes, verifies ownership and grants, and checks that all original business table counts/functions and release controls remain unchanged. It supports a transactional dry run and records the applied review in MIGRATION_REVIEW.json. No source business row, existing officer assignment or managed Auth relation was changed by these migrations.

1. `20261027193348_phase16_processing_and_discovery.sql`: leased processing, indexed candidates, versioned translation/category provenance, restricted metadata discovery, safe access-request linkage and more efficient current-authority helpers.
2. `20261027194500_phase16_private_attachment_scanning.sql`: forced-RLS scanner receipts, exact hash/size/file binding, strict CLEAN and human-verification policies.
3. `20261027200002_phase16_hosted_deadline_notifications.sql`: reviewed rules, deduplication receipts and a narrow nonowning NOLOGIN/NOBYPASSRLS notifier with no complaint body/document privileges.

No public schema exposure or blanket table grants were added. Public direct case RPCs remain closed. The application login still cannot assume table/function-owner roles or enable its own release.

## Executed evidence and limits

- DATABASE_RESULTS.json: disposable PostgreSQL 18 baseline/migration replay, authorization assertions, core workflow transactions, two-Bureau case/document/operation isolation, suspension, revocation, metadata discovery, independent access grant/revoke, scanner clearance and reminder deduplication. The SQL authorization fixtures use synthetic claims and explicitly mocked scanner/provider responses. The additional development-provider checks execute real Google Cloud Translation and Gemini calls with synthetic Hindi complaint data and persist actual output/provenance in that disposable database. They do not write hosted complaints.
- HOSTED_SESSION_RESULTS.json: actual issued JWTs from the three existing approved account passwords, real login/refresh/online user checks, fresh-test-session-only logout and denied refresh/application replay. Both legacy direct RPCs are ACL-denied before and after logout; this does not prove safe reopened RPCs. No browser, managed-schema changes or role mutations.
- HOSTED_NEGATIVE_RESULTS.json: actual deployed Supabase, restricted web login and verified TLS; no-identity read denial, private endpoint denial and disabled-release enforcement. No identity impersonation, mailbox read or business mutation.
- HTTP_AUTH_RESULTS.json: real local production Next HTTP against actual Supabase Auth and the restricted hosted gateway for all three approved accounts; login, profile, current session, account-only snapshot, administrator-only current catalog checklist, refresh, application logout and stale-cookie replay rejection. Only new test sessions were logged out; no complaint writes or release activation.
- HTTP_RESULTS.json: real local Next production HTTP with synthetic public/provider configuration; negative OAuth state/origin, secure cookie, cron bearer and disabled workflow boundaries. No real hosted account or mailbox success is inferred from these checks.
- Root unit tests and private-scanner HTTP/TCP transport tests distinguish mocked transports from real services. No real end-to-end ClamAV scan has passed because no approved endpoint is configured.
- Final browser acceptance is reserved for the user. Hosted positive complaint writes, a first actual email ingestion, scanner acceptance and independent activation review remain distinct acceptance steps. Supabase advisor refresh was denied by connector permissions during final checks; catalog checks are not represented as a successful advisor run.

## Configuration and manual acceptance

Use only dedicated server values on Vercel Production; never copy an entire local environment file. The approved Google fields are SYNAPSE_GEMINI_EMBEDDINGS_API_KEY, SYNAPSE_GOOGLE_TRANSLATION_KEY and SYNAPSE_DEV_EXTERNAL_PROCESSING_APPROVED. The last flag approves development/test data only; turn it off before processing unapproved production complaint data. Gmail uses its existing separate OAuth client, encrypted private database storage, approved address and CRON_SECRET. The fourth Auth-testing mailbox remains excluded from ingestion.

Private scanner preparation uses ignored `.env.integrations.local`: SYNAPSE_SCANNER_URL, SYNAPSE_SCANNER_TOKEN and SYNAPSE_SCANNER_PRIVATE_APPROVED. The URL must be an approved HTTPS `/scan` endpoint reachable from Vercel. Deploy the supplied adapter only on existing approved private infrastructure behind TLS; keep clamd private and signatures updated. See services/scanner/README.md for the protocol, limits, deployment and harmless/EICAR acceptance procedure. No endpoint or paid resource has been invented. Keep downloads quarantined until actual acceptance.

See RELEASE_REVIEW.md for the bounded release and original-dashboard manual test sequence. Current disabled controls are reported honestly; UI text is not a substitute for activation approval.

## Reproduction

Run `npm test`, `npm run test:scanner`, `npm run baseline:check`, `npm run typecheck`, `npm run lint`, `npm run test:database:operations`, `npm run build`, then `npm run test:http:gmail`. The database harness refuses non-loopback destructive targets and uses a disposable UUID database. With approved local development-provider keys, `node --env-file=.env.integrations.local --import tsx scripts/test-database.mjs --operations --real-providers` adds actual provider calls. The current-account Auth runner is `node --env-file=.env.local --import tsx scripts/phase16/verify-sessions.mts --approved-current-account-vault`; it requires the existing ignored Windows-encrypted approved-account vault and logs out only its newly created test sessions. Never load `.env.operator.local` into the web process.
